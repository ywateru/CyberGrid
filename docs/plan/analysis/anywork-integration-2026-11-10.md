## 1. 判断

反馈整体合理。CyberGrid 已有原生安全连接和协调恢复基础，但浏览器目前只有只读目录 SDK，尚不足以让接入方直接构成统一的远程工作区产品。主要缺口在产品应用绑定、持续授权、状态可观察性、浏览器安全通道及关闭语义。

建议短期正式支持安全桥接扩展，保留当前 JS SDK 的只读定位；先以 Rust 宿主、JS 目录及外部安全桥接完成共同样例。完整浏览器端到端传输作为单独方案评估，不能靠返回一个 URL 或把原生实现编译为 WASM 就承诺支持。

建议提前处理三项原反馈列为 P1 的问题：CG-10 的本机关闭语义、CG-11 的静态允许应用配置，以及 CG-07/12 中影响 RAM-only 长期运行的注册 fence 生命周期。原有 WebRTC、iroh、Cloudflare 路径不需要重写。

## 4. 关键方案与边界

### 4.1 浏览器先采用正式安全桥接扩展

浏览器不能直接使用 Rust 当前的原生 TCP、iroh QUIC 或自定义内层 mTLS 字节栈。即使 WebRTC DataChannel 可用，身份绑定、流封装、加密、信令权限和关闭仍需设计；现有 console bearer 也没有设备信令权限。

短期由 CyberGrid 提供经过账号目录验证的目标身份、目标能力及版本化连接描述；桥接适配器返回已认证的双向通道。AnyWork 保留其业务权限和请求/PTY 语义。浏览器端加密协议若由桥接负责，应审查已有方案和实现，不在分析阶段发明密码协议。

必须区分设备级加密传输入口、端口 HTTP 入口及浏览器安全桥接入口。每种能力明确支持哪些平台和协议，未支持时返回不可用原因，不能取一个 URL 作为另一种入口的替代。端口 URL 更新与失效需要版本/事件，协商失败不得退回明文。

### 4.2 产品绑定与静态目录一起交付

当前 appId 同时充当 OAuth Native client ID 和设备隔离命名空间。建议将真实 OAuth client 与产品命名空间分开；产品命名空间可采用规范应用 ID 或稳定产品 key，具体字段在设计时确定。

服务端配置声明固定 issuer/resource、允许的 SPA/Native client 集合及配置版本。应用仍在 Logto 创建和管理，CyberGrid 只保存映射/允许策略，不重新增加应用管理后台或应用数据库。

静态模式不要求 Management M2M，也不在每次设备请求时依赖应用目录网络调用。静态策略更新后的失效窗口、已禁用 Logto 应用的会话处理必须明确；移除动态目录依赖不能等同于获得即时撤销。采用新映射要检查 Store 的 user/app 隔离、信令、幂等派生和 SDK 身份比较，并提供协议迁移方案，不能静默改变旧 appId 的含义。

### 4.3 三种会话与单一刷新所有者

| 层 | 所有者与作用 | 需要补充 |
| --- | --- | --- |
| Logto 授权/token | 官方 SDK 或明确的 grant owner | 足够新鲜的资源 token、单飞刷新、换号检测；刷新结果未知时不能重放旧 grant |
| CyberGrid 协调 session/在线租约 | CyberGrid SDK + 服务端 | 24 小时 session 与 65 秒 lease 的恢复/过期事件；持续重新授权及 Logto 撤销的生效策略 |
| AnyWork 业务授权/业务连接 | 工作区宿主与安全桥接 | 短期授权更新、拒绝更新后关闭业务、HTTP/PTY 恢复及写操作去重；不由 SDK 盲目重放 |

`minValidity` 是向宿主的要求，不替代服务端验签。拒绝授权、账号改变、超预算和暂时网络故障需要不同结果。对过期缓存 token 的受限刷新应使用新的已验证授权，不重复提交已经消费且结果未知的刷新 grant。

RAM-only 优先由宿主官方 Logto SDK 保持刷新权，Rust AuthProvider 只请求 access token。若 Rust 必须成为刷新所有者，则需真正支持内存 grant 交接和清理，不能为了复用当前文件交接而暗中落盘。桌面与本地 Web 可通过受限本机会话共享账号摘要和本机状态，不转交 Native refresh token；本机桥接仍需 origin、CSRF、防重绑定和作用域边界，不能仅凭 loopback 地址放行。

### 4.4 状态应按层组合

建议快照分别包含 `identity`、`coordination`、`publication`、`reachability` 和宿主提供的 `businessAuthorization`，各自带固定 reason。`online` 仅表示租约有效，`ready` 必须限定在哪一层。

发布操作至少区分本地意图已接受、服务端已确认的 revision、目标可尝试连接和实际业务连接成功。订阅同时提供当前快照和后续事件，携带单调版本/代际；事件丢失可重取快照，防止订阅建立前已就绪却一直显示准备中。协调不可达时状态为未知，不能继续展示缓存的可连接结论。

### 4.5 关闭与 RAM-only 身份不宜后置

“关闭远程”必须本机优先执行，保证断网时也能拒绝新流并终止活跃远程 HTTP/PTY；随后撤回发布并尽力撤销协调会话。停止业务访问、隐藏设备、注销协调 session 和退出 Logto 分别返回真实结果。只执行 `unexpose()` 不足以定义该产品语义。

稳定安装 ID、当前注册 key/deviceId、incarnation 和加密公钥分别建模。非敏感安装 ID 可用于 owner/product 限定的展示关联；同一安装 ID 带新公钥时仍按换钥策略确认。

当前 fence 在 namespace 生命周期内保留，`close()` 不回收，新 Client 会生成新注册 key。默认每用户 128、全局 2048 个键的上限意味着 RAM-only 长期反复启动存在容量风险；这是静态可推导的边界，具体用户体验仍需定向复现。需要安全退役/有限保留方案，同时保持旧 revision 不可复活。不能简单给 fence 加 TTL、静默驱逐或定期重置整个 namespace 来掩盖问题。

Redis 还有用于派生幂等注册回执的共享 seed，它属于中央协调秘密，不是业务解密私钥。保留清单应分别列出会话 hash、设备/发布信息、信令、幂等记录、fence、seed、限流/等待记录，并说明逻辑过期、请求触发的物理清理及运维删除/重置影响。无请求时不会自动完成当前 Lua 的懒清理。

| 链路 | 谁创建/调用/注入谁 | 真实集成验收 |
| --- | --- | --- |
| 产品配置 → 登录 → 服务授权 | 部署者配置允许策略；宿主创建官方 Logto client；SDK核公开配置；服务端校验真实 token client 并解析产品 | 真实 Logto SPA 与 Native 分别登录；允许集合及账号隔离，不只测静态夹具 |
| 宿主 token owner → SDK恢复 → 协调交换 | 宿主注入 token provider；SDK请求新鲜 token；服务端验签并受 fence 保护地注册 | 正常过期、刷新失败、交换结果未知及换号；不出现双刷新者 |
| Rust宿主 → 发布确认 → JS目录 | 本地业务授权后宿主调用 expose；协调服务确认 revision；JS读取/订阅该版本 | 发布前/后、地址更新/撤回、服务重置、租约过期；不把本地意图成功当远端确认 |
| JS目录 → 桥接适配器 → Rust宿主/业务 | JS核目标绑定；桥接验证身份并加密；工作区检查业务授权后执行 | 桌面浏览器、Android Chrome、iOS Safari 分别验证；设备级 URL 不顶替业务端口 |
| 本机关闭 → 活跃连接 → 云端撤回 | 本机先封入口和流；SDK/桥接清理；服务记录撤回/撤销结果 | 协调在线与断网两种情况；本地工作继续；迟到恢复不能重新发布 |
| 安装关联 → 新运行身份 → fence退役 | 宿主提供非敏感安装 ID；服务按验证 owner/product 关联；新运行钥匙独立验证 | 多次新建 Client、同时启动、换钥拒绝/确认、退役旧请求；无身份偷换或容量逃逸 |
| SDK事件 → 产品UI | SDK提供快照/事件；AnyWork组合业务授权状态 | 先就绪后订阅、事件丢失、后台恢复、目录不可用；UI状态符合真实层级 |

本地 Web 的受限本机会话由 AnyWork 创建；CyberGrid 提供参考边界，不增加云端业务票据服务。每条链都需要用真实模块验证，不能用各模块 mock 测试通过代替。

## 7. 推荐顺序和验收门槛

1. **先定契约与授权口径。** 选定短期安全桥接路线、产品 client 绑定、会话/撤销窗口、RAM-only 所有者、关闭语义及 SDK 嵌入/分发许可。列清一期支持 Mac 宿主、桌面 Web、手机浏览器的范围。
2. **交付最小可用集成底座。** M1/M2/M3：静态允许策略、新鲜 token 请求、分层快照、发布确认、可取消连接、本机关闭、注册键容量方案。复用既有协调恢复。
3. **打通共同样例。** M4/M5：安全桥接、受信生产入口、Mac + Web + 手机浏览器同账号进入同一工作区；先测正常和拒绝路径，再谈替换全部旧入口。
4. **完善规模化能力。** 目录 watch、设备别名/长期离线展示、完整诊断、更多平台和独立浏览器传输方案。watch 的目录 revision 不能与信令 cursor 混用，也不能把全局 revision 直接当用户增量流。

验收建议采用反馈中的分层矩阵：先验证本地不依赖云、全新两端登录/明确开启、发布确认、关闭和隔离；再做 30 分钟且跨至少 6 个短授权周期、8 小时和超过 10,000 混合请求；24 小时协调到期单独用可控时钟或长跑测试。加入多次进程重建的 fence 容量反例，不能仅长时间复用一个 Client。

5 秒目录收敛、60 秒完整连接预算、1 秒取消 UI 是建议目标，须明确计时起点、网络前提和平台挂起例外，测出基线后再写保证。当前默认串行传输预算为 12+8+35 秒，尚未包含所有配置/协调/授权等待，不能据此直接宣称已有 60 秒端到端上限。

现有 Wi-Fi/4G 原生公网任务继续独立推进；本分析不能替代该验收，也不能用其结果证明手机浏览器已支持。

## 8. 责任分工与不应扩大之处

CyberGrid 负责协调和通用安全连接契约；AnyWork 负责工作区业务权限、业务请求/终端恢复、本机远程开关、界面导航和旧入口退役。反馈所述短期业务票据未续期、图片路径问题仍属于 AnyWork，不能靠延长 CyberGrid session 修复。

不增加云端业务内容库、通用内容反向代理、另一套用户系统或跨账号分享。Logto 可保存少量配置，但在线状态/频繁发布仍走协调存储；其是否适合保存设备偏好需另外核对更新权限、配额与并发语义。

自有域名和生产 provider 的支持，不等于承诺免费无限中继或任意网络必直连。地址和端口可作为必要协调元数据保存，业务正文、终端内容和解密私钥继续留在终端。托管前端代码、首次公钥发现与目录完整性仍属于信任边界。

原项目的对外许可应由所有者明确；本分析不更改 LICENSE。AnyWork 的统一界面与旧入口退役也不能先于替代路径真正达到其目标平台和业务验收。
